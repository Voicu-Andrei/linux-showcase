## Speaker 1 — Live Process Inspection

### Goal

Show that Linux exposes live process information through files in
`/proc/<pid>/`.

### Say

Linux has a virtual filesystem called `/proc`. These files are not normal
files stored on disk. They are generated by the kernel when we read them.
For every running process, Linux creates a directory named `/proc/<pid>`.
That directory exposes the process arguments, state, memory information,
environment, and open file descriptors.

### Commands

Start a process we can inspect:

```bash
./part1/launch-target.sh &
T=$!
```

Show that the process has a `/proc` directory:

```bash
ls /proc/$T/
```

Show the command line arguments:

```bash
tr '\0' ' ' < /proc/$T/cmdline; echo
```

### Say

The command line is separated by NUL bytes because that is how arguments
are stored internally after `execve()`. We use `tr` only to make it readable.

Show process metadata:

```bash
grep -E '^(Name|State|Pid|PPid|VmRSS|Threads):' /proc/$T/status
```

### Say

This is a readable view of kernel process metadata. `State` tells us how
the scheduler currently sees the process. `PPid` shows its parent process.
`VmRSS` shows how much physical memory is resident. `Threads` shows the
number of threads in this process.

Show open file descriptors:

```bash
ls -l /proc/$T/fd/
```

Resolve two file descriptors:

```bash
readlink /proc/$T/fd/3
readlink /proc/$T/fd/5
```

### Say

File descriptors are also visible through `/proc`. This is the same basic
idea used by tools like `lsof`: they inspect `/proc/*/fd/` to see what
files processes have open.

Optional, only if there is time:

```bash
readlink /proc/$T/exe
readlink /proc/$T/cwd
```

Clean up:

```bash
kill $T
```

Transition:

The first part showed a live process. The next part shows what remains
after a process has exited but has not been collected by its parent.

## Speaker 2 — Zombie Process And Reaping

### Goal

Show that a zombie is an exited process whose parent has not called
`wait()` yet.

### Say

When a child process exits, the kernel cannot delete everything
immediately. The parent may still need the child's exit status. Until the
parent calls `wait()`, Linux keeps a small process table entry. That state
is called a zombie.

### Commands

Create a zombie:

```bash
./part2/zombie-maker.sh &
P=$!
sleep 1.5
Z=$(cat scratch/zombie-child.pid)
```

Show it in `ps`:

```bash
ps -o pid,ppid,stat,comm,cmd -p $Z
```

### Say

The `STAT` column shows `Z`, which means zombie. The process is not running
anymore. It is already dead, but the kernel is keeping its PID and exit
status until the parent collects it.

Show the kernel view:

```bash
grep -E '^(Name|State|PPid):' /proc/$Z/status
```

### Say

`/proc` confirms the same thing: `State: Z`. A zombie has no user code left
to run, so sending `kill -9` to the zombie itself would not solve the
problem. The parent must call `wait()`, or the parent must die so PID 1 can
inherit and reap the zombie.

Show the parent:

```bash
ps -o pid,stat,comm,cmd -p $P
```

### Say

The parent is now `sleep infinity`. It never calls `wait()`, so the child
stays as a zombie.

Kill the parent:

```bash
kill $P
sleep 0.5
ps -o pid,ppid,stat,comm -p $Z 2>&1
```

### Say

After the parent dies, the zombie becomes an orphan and is inherited by
PID 1. PID 1, usually `systemd`, has the special responsibility of reaping
orphans. Once it calls `wait()`, the zombie disappears.

Transition:

Now that we have seen process state directly in `/proc`, the final part
uses that idea to build a tiny process watcher.

## Speaker 3 — Process Watcher

### Goal

Show that a small shell script can monitor a process by reading `/proc`.

### Say

Because Linux exposes process state as files, a monitoring tool does not
need a complicated interface for a basic demo. It can repeatedly read
`/proc/<pid>/status`. When the process is gone, the file disappears.

### Commands

Show the script:

```bash
cat part3/proc-watch
```

### Say

The important line is `STATUS=/proc/$PID/status`. The script loops while
that file is readable, extracts the `State:` line with `awk`, and prints
the state once per second.

Confirm it is available:

```bash
which proc-watch
```

If nothing prints:

```bash
export PATH="$HOME/.local/bin:$PATH"
```

Run it from another directory:

```bash
cd /tmp
sleep 8 &
proc-watch $!
cd -
```

### Say

While `sleep` is alive, the watcher prints its state from
`/proc/<pid>/status`. When the process exits, `/proc/<pid>/status`
disappears, so the watcher knows the process is gone.

Optional, only if there is time:

```bash
./part2/zombie-maker.sh &
sleep 1.5
Z=$(cat scratch/zombie-child.pid)
P=$(cat scratch/zombie-parent.pid)
( sleep 5; kill $P ) &
proc-watch $Z
```

### Say

This optional example connects back to Part 2. The watcher prints
`Z (zombie)` while the zombie still exists, then stops once PID 1 reaps it.

## Closing Recap

### Say

This project showed three views of the same operating system idea.
First, `/proc/<pid>` let us inspect a live process using ordinary file
commands. Second, it let us observe a zombie process and understand why
parents must call `wait()` and why PID 1 reaps orphans. Third, it let us
build a small watcher that monitors process lifetime by reading kernel
generated files.

The main takeaway is that `/proc` turns kernel process state into a
filesystem interface. That is why tools like `ps`, `top`, and `lsof` can
be powerful while still being based on simple file reads.

## Likely Professor Questions

### Why is `/proc` called a virtual filesystem?

Because the files are not stored on disk. The kernel generates their
contents when a process reads them.

### What is the difference between an orphan and a zombie?

An orphan is still running, but its parent died. A zombie has already
exited, but its parent has not collected its exit status.

### Why can we not kill a zombie?

Because it is already dead. There is no running code left to receive the
signal. It disappears only when its parent, or later PID 1, calls `wait()`.

### What do tools like `ps` and `lsof` use?

They read files under `/proc`. `ps` reads process status files, while
`lsof` walks `/proc/*/fd/` to inspect open file descriptors.

### What is one limitation of `proc-watch`?

It polls once per second and can theoretically race with PID reuse. Modern
Linux has `pidfd_open` for a stronger production-grade solution.
